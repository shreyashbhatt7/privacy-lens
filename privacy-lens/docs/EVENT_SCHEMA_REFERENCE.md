# TrackingEvent Schema — Verified Against Code (Person 1's network/ layer)

Generated by reading `lib/event-schema.js` and every `createTrackingEvent()` call
site in `network/*.js` directly — not copied from a prior doc. If this
disagrees with `ARCHITECTURE_LOCK.md`, **this is the ground truth until the
team explicitly agrees to change the code instead.**

## Enforced shape (from `lib/event-schema.js`)

```
{
  id: string,              // auto-generated, e.g. "evt_1789192983465_736"
  timestamp: number,       // auto-generated, Date.now()
  tabId: number | null,
  site: string | null,     // top-level eTLD+1 the user is browsing
  category: "fingerprinting" | "network" | "storage" | "identifier",
  subtype: string,         // free-form, detector-defined (see table below)
  source: object,          // shape VARIES by detector — see table below
  target: object,          // shape VARIES by detector — see table below
  evidence: object,        // FLAT, detector-defined fields — NOT nested under `.details`
  severity: "low" | "medium" | "high",
  confidence: number       // 0.0–1.0
}
```

`createTrackingEvent()` only validates `category`, `severity`, and `confidence`.
It does **not** enforce any internal shape for `source`, `target`, or `evidence`
beyond "these are objects." Anything consuming events must branch on
`category`/`subtype` to know what keys to expect.

## What each of Person 1's four detectors actually emits

| Detector | category | subtype | source | target | evidence |
|---|---|---|---|---|---|
| etag-detector.js | `identifier` | `etag` | `{ requestDomain }` | `{ domain }` | `{ api, valueHash, timesSeen, distinctSitesSeenOn }` |
| cache-detector.js | `identifier` | `cache-token` | `{ url }` | `{ domain }` | `{ api, immutable, maxAgeSeconds, pathLooksTokenized }` |
| cname-detector.js | `network` | `cname-cloaking` | `{ requestHostname }` | `{ domain }` | `{ api, cnameChain }` |
| thirdparty-detector.js | `network` | `beacon` \| `third-party-load` | `{ script }` (hostname string or null) | `{ domain }` | `{ api, url }` |

## Corrections to make wherever the stale doc claims otherwise

1. **`evidence.details` does not exist anywhere in the code.** All evidence
   fields are flat and detector-specific (see table). If the correlation
   engine or any doc references `evidence.details.*`, that's drift — either
   fix the doc or refactor every detector to nest under `details`, but pick one.
2. **`source.script` is not a universal field.** Only `thirdparty-detector.js`
   uses the key `script`, and even there it's just a hostname string (e.g.
   `"googlesyndication.com"`), not a full script URL, and can be `null` for
   opaque/unresolvable initiators. The other three detectors use different
   key names entirely (`requestDomain`, `url`, `requestHostname`).
3. **`target.domain` is consistent** across all four detectors — this part
   of the prior doc's claim is accurate and doesn't need to change.

## RESOLVED at hour 18-24 integration (Person 1 + Person 2 merge)

Decision: **Option B, but only enforced at the background ingestion
boundary** — a hybrid that needed zero rework on either side's existing
detector code:

- Person 1's four network detectors (`etag`, `cache-token`,
  `cname-cloaking`, `beacon`/`third-party-load`) already call
  `createTrackingEvent()` directly from the background service worker with
  flat evidence — unchanged, since they already produce the canonical shape.
- Person 2's fingerprint hooks still produce a **draft** via
  `createFingerprintDraft()` in `shared/events.js` (nested
  `evidence.details`, no `tabId`/`site` — those aren't knowable from page
  context). This is unchanged from Person 2's original code.
- The new piece: `background.js` now listens for
  `PRIVACY_LENS_BATCH_EVENTS` messages from `content-bridge.js`, and its
  `finalizeFingerprintDraft()` helper is the ONE place that converts a
  draft into a real `TrackingEvent` — flattening `evidence.details` into
  `evidence` and filling `tabId`/`site` from `sender.tab`, which is only
  available once the message reaches the background worker.

Net effect: every event that lands in `chrome.storage.session` (and
therefore everything the panel UI / correlation engine will ever see) has
flat evidence and populated `tabId`/`site`, regardless of which detector
produced it. `source`/`target` key names are still detector-specific (see
table above) — that part of Option A's "consumers branch on category/
subtype" still applies and is unavoidable without renaming fields in the
network detectors, which wasn't necessary for this fix.

If the correlation engine (Person 3) ever needs `source.script` universally
present rather than the current per-detector key names (`requestDomain`,
`url`, `requestHostname`, `script`), that's a separate, still-open
refactor — not addressed here.

## Phase 24–32 Update: Confidence & Correlation Engine Evidence Fields

With Person 3's Confidence Engine (`detection/confidence-engine.js`) wired into `background.js` during draft finalization, finalized fingerprint events now include additional forensic correlation metadata within the flat `evidence` object:

| Field | Type | Description |
| :--- | :--- | :--- |
| `evidence.correlatedVectors` | `Array<string>` | Active vector groups detected for this script session within the 10s correlation window (e.g. `["canvas", "webgl", "audio", "beacon"]`). |
| `evidence.forensicNotes` | `string` | Human-readable explanation of why the event was scored at its severity (e.g. `"Active Multi-Vector Exfiltration Chain -> [tracker.com] | Vectors: Canvas + WebGL (Unmasked GPU) + AudioContext"`). |
| `evidence.count` | `number \| undefined` | Present if rapid polling occurred (`count > 1` within batch window). |

### Severity and Confidence Agreement:
- `high`: `confidence >= 0.70`
- `medium`: `0.40 <= confidence < 0.70`
- `low`: `confidence < 0.40`
*(Both Person 1's network detectors and Person 3's confidence engine now use identical 0.40 / 0.70 severity thresholds).*
